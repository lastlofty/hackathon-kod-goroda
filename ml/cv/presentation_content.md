# Презентация — содержание (3 минуты, 7 слайдов)

Цифры — из `runs/eval/cv_metrics.json` (групповая кросс-валидация), `runs/robust/resolution_metrics.json`,
`runs/pano/`. Всё посчитано на итоговой модели; ничего не настраивалось по панорамам.

---

## 1. Мониторинг шкафов связи по фото  (~15 с)
**На слайде:** название; подзаголовок «фото → шкафы ТКШ и РЩ → состояние, приоритет, рекомендация → реестр и карта»;
фото с рамками (пример: `runs/pred/annotated/tksh_lkp_20251015.jpg` или `Фото.1.jpg`).

**Речь:** Бригады МГТС проезжают до 100 км за выезд. Мы сделали прототип, который по фото находит шкафы связи,
оценивает их состояние и выдаёт бригаде список «что чинить и в каком порядке».

## 2. Как работает  (~30 с)
**На слайде — схема в одну строку:**
Фото → **OWLv2** находит шкафы (без обучения, по тексту) → вырез → **DINOv2 + CLIP** признаки
→ классификаторы: тип, дефект, коррозия, механика (+ zero-shot CLIP для коррозии) → **приоритет P1–P4**
→ сервис: реестр, карта 2ГИС, решение оператора.

**Речь:** Данных мало — 61 фото без рамок, поэтому мы не обучали детектор с нуля. Шкафы находит
zero-shot-детектор по текстовому запросу, а состояние оценивают лёгкие классификаторы поверх признаков
больших предобученных моделей. Новый тип объекта — колодец или опора — это новый запрос и небольшая разметка.

## 3. Результат для бригады  (~25 с)
**На слайде — таблица:**

| приоритет | когда | статус | рекомендация |
|---|---|---|---|
| P1 критический | нарушено крепление, висит на кабеле | Срочно* | немедленный выезд |
| P2 высокий | механическое повреждение | Срочно* | ремонт / замена в ближайший выезд |
| P3 средний | коррозия ЛКП | На проверку | плановая окраска |
| P4 | дефекта нет | Без замечаний | — |

\* «Срочно» — только если модель уверена (вероятность ≥ 0.5); при меньшей уверенности тот же объект идёт
«На проверку» с рекомендацией «осмотреть: возможно — механическое повреждение».
Плюс вердикт «В норме / Повреждён / Требует проверки» и скриншот карточки объекта в сервисе.

**Речь:** Для каждого объекта — вердикт, приоритет и конкретная рекомендация. Результат сразу попадает в
реестр сервиса: сначала «Срочно», оператор подтверждает или исправляет решение модели.

## 4. Как мерили и подбирали пороги  (~35 с)
**На слайде — слева схема протокола, справа таблица.**

Протокол (схема из трёх шагов):
1. **Групповая кросс-валидация.** 61 фото → 51 группа: почти одинаковые снимки одного объекта (соседние номера
   файлов) всегда вместе. По очереди откладываем одну группу, обучаем на остальных, предсказываем отложенную.
2. **Пороги — по отложенным предсказаниям, по цене действия.** «На проверку» — наибольший порог с полнотой ≥ 90%
   (пропустить повреждение дороже лишнего осмотра). «Срочно» (внеплановый выезд дороже) — только при p ≥ 0.5.
   Пороги фиксируются и сохраняются в модель.
3. **Метрики — на тех же отложенных предсказаниях** с выбранными порогами. Панорамы в подборе не участвуют.

| задача | AUC | порог | полнота | точность | на 61 фото |
|---|---|---|---|---|---|
| повреждён / в норме | **0.96** | 0.50 | 0.93 | 0.88 | найдено 38 из 41 повреждённых; 5 из 20 исправных — лишняя проверка |
| механика → «На проверку» | 0.96 | 0.14 | 0.91 | 0.73 | 19 из 21; 7 лишних осмотров |
| механика → «Срочно» | 0.96 | 0.50 | 0.67 | **0.93** | 14 из 15 срочных — реальные повреждения |
| коррозия | 0.92 | 0.33 | 0.91 | 0.70 | 21 из 23; 9 лишних |
| тип ТКШ / РЩ | 0.97 | 0.50 | 0.90 | 0.96 | 4 ошибки из 61 |

Сноска: для «повреждён» порог 0.5 уже даёт полноту 0.93, поэтому его не снижали; для механики и коррозии
порог «На проверку» снижен, чтобы не пропускать дефекты, — цена видна в столбце «точность»; «Срочно» остаётся
на 0.5, чтобы не гонять бригады по ложным тревогам.

**Речь:** Метрики считаем на кросс-валидации, где снимки одного объекта не оказываются одновременно в обучении
и проверке. Пороги подобраны там же, по отложенным предсказаниям, на полноту 90 процентов — тестовую выборку и
панорамы для этого не трогали. Два порога по цене действия: на проверку уходят 9 из 10 повреждённых шкафов,
а среди срочных выездов 14 из 15 — по делу.

## 5. Что мы поняли  (~25 с)
**На слайде — два факта:**
- **Качество = качество выреза.** Тот же классификатор на авто-вырезе и на правильном: коррозия AUC 0.73 → 0.93,
  «повреждён» 0.89 → 0.96. Главный рычаг развития — детектор.
- **Устойчивость к разрешению.** Обучение на копиях в нескольких разрешениях: «повреждён» держит AUC 0.96 → 0.96
  при уменьшении фото до 384 px (без этого — 0.97 → 0.94). Детекция при этом падает: 70% → 57% попаданий.

**Речь:** Классификатор уже хорош, если ему показать шкаф целиком; узкое место — найти шкаф. На маленьких
фото классификация держится, а поиск шкафа проседает.

## 6. Проверка на уличных панорамах  (~25 с)
**На слайде:** 2–3 панорамы с рамками (`runs/pano/annotated/moscow-001.jpg`, `moscow-005.jpg`, `moscow-006.jpg`).
- 20 панорам 896×576, как с камеры автомобиля; не использовались ни для какой настройки.
- Шкафы найдены на 9 из 20 кадров: 19 объектов → 1 «Срочно», 13 «На проверку», 5 «Без замечаний».
  Щит у дороги — «в норме», ящики на опорах — «на проверку» (коррозия).
- Двойной порог: ложных «Срочно» стало 1 вместо 3 — остался ящик 43×38 px с «креплением».
- Честно: объекты по 12–70 px → много «требует проверки»; 16 ложных срабатываний на кнопке интерфейса карт
  (артефакт скриншота, с камеры авто его не будет).

**Речь:** На панорамах прототип находит шкафы, но объекты там в десять раз меньше, чем в датасете, и модель
чаще сомневается — такие объекты уходят «На проверку», а не в срочный выезд. Это и определяет следующий шаг.

## 7. Путь к камере на автомобиле  (~25 с)
**На слайде — шаги:**
1. Видео → кадры каждые N метров по GPS, отсев смазанных.
2. Трекинг объекта через кадры → **взвешенное решение по всем наблюдениям**: оценки дефекта с разных кадров
   усредняются с весом по качеству кадра (размер шкафа в кадре, резкость, уверенность детектора). Крупный
   резкий кадр весит больше далёкого и смазанного; одна случайная ошибка не даёт ложной тревоги, а дефект,
   видный только с одного ракурса, не теряется. Итог — одна запись на объект и лучший кадр как доказательство
   (поля `observations` и `best_det_id` уже есть в контракте сервиса).
3. Координаты из GPS-трека авто → адрес в отчёте по итогам поездки.
4. Дообучение детектора на собранных рамках и решениях операторов; класс «не шкаф».
5. Инференс на GPU через Triton — инфраструктура уже в репозитории.

**Речь:** Сервис уже принимает фото, видео и GPS-трек. Камера на авто видит каждый шкаф на нескольких кадрах —
трекинг объединяет их, и решение принимается по всем кадрам с весами, а не по одному снимку. Это напрямую
закрывает слабое место, которое мы видели на панорамах: далёкий мелкий кадр сам по себе ненадёжен, а серия
кадров при подъезде — нет. Дальше — дообучить детектор на реальных проездах и замкнуть цикл: решения
операторов становятся разметкой. Спасибо!

### Запасные факты для вопросов
- Данные: 61 фото, 6 классов; признаки из описаний: коррозия 23, МП 21, крепление 5, нет двери 2.
- Нарушение крепления: 5 примеров — модель не обучается; P1 пока ставится ненадёжно.
- Зачем групповая CV: обычный leave-one-out давал «повреждён» AUC 0.973, групповая — 0.957. Разница —
  утечка через почти одинаковые снимки одного объекта; на слайдах только групповые цифры.
- Честная оговорка: конфигурацию (мульти-разрешение, ансамбль только для коррозии) выбирали из нескольких
  вариантов по той же CV, поэтому цифры могут быть немного оптимистичны; независимая проверка — тест организаторов.
- Ансамбль с zero-shot CLIP помогает только коррозии (0.91 → 0.92); на механике zero-shot слабый (0.57),
  поэтому там не используется.
- 18 из 61 целевых рамок для обучения проставлены вручную (детектор не находит разбитые/открытые щиты целиком).
- Скорость (RTX 5050, 8 ГБ): 4 фото за 15 с вместе с загрузкой трёх моделей; детекция всех 61 фото — около минуты.
