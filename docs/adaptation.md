# Как адаптировать backend под новое ТЗ

## Что сначала выяснить

До добавления кода зафиксируйте:

1. Какие данные поступают: файлы, ссылки, видеопоток, телеметрия или ручной ввод.
2. Какие предметные объекты существуют и какие поля для них обязательны.
3. Какие результаты выдаёт обработка: классы, bbox, маски, текст, числовые показатели, рекомендации.
4. Нужна ли история, ручное подтверждение и роли пользователей.
5. Как запускается обработка: синхронно, через очередь, пакетно или внешним сервисом.
6. Где должны храниться файлы и каков ожидаемый объём.

Без этих данных нельзя подтвердить необходимость конкретной очереди, объектного хранилища, PostGIS или схемы авторизации.

## Что меняется конфигурацией

Без миграции и изменения ORM можно:

- создать workspace для нового ТЗ;
- определить любое число entity types;
- задать обязательные и допустимые поля через JSON Schema;
- хранить дополнительные поля entity, media и finding в `attributes`;
- использовать свои `kind`, `pipeline`, `category`, `label` и `status`;
- хранить bbox, polygon или иную геометрию в `geometry`;
- настроить UI-справочники и значения по умолчанию в `workspace.settings`.

## Когда нужен новый код

Новый service или adapter нужен, если появляется:

- вызов конкретной модели или внешней системы;
- бизнес-правило, которое нельзя выразить JSON Schema;
- вычисляемый агрегат или отчёт;
- авторизация и разграничение workspace;
- асинхронная очередь и повторные попытки;
- S3/MinIO вместо локальной папки;
- специализированный пространственный запрос.

Геокодирование уже вынесено в adapter `app/integrations/dgis.py`. Если провайдер изменится, новый клиент должен реализовать эквивалентные операции поиска и обратного геокодирования, а предметные таблицы менять не требуется.

Предметное правило размещается в `app/services`. Клиент внешнего сервиса или worker не должен находиться внутри HTTP-route.

## Рекомендуемый порядок адаптации

1. Создать workspace и записать общие справочники в `settings`.
2. Создать entity types и проверить JSON Schema на примерах.
3. Зафиксировать контракт входного media и выходного finding.
4. Реализовать adapter/worker, который создаёт и обновляет processing jobs.
5. Добавить интеграционные тесты с фактическими примерами нового ТЗ.
6. Только после измерений добавить очередь, объектное хранилище или георасширения.

## Критерий хорошей адаптации

Если новое ТЗ отличается только названиями объектов, полями, классами модели и статусами, должны измениться данные workspace/entity types и worker, но не первоначальная миграция и не универсальные CRUD-маршруты.
